# Чек-лист для ревью (по комментариям Ultimatereo, KotlinLearning PR #9)

Собрано на основе реальных замечаний ревьюера к PR
https://github.com/lenyaplay/KotlinLearning/pull/9. Пункты обобщены до
переиспользуемых правил, чтобы проверять по ним будущий код перед отправкой
на ревью.

## Репозиторий и конфигурация

- [ ] `.idea/`, `local.properties` и прочие машинно-зависимые файлы не
      закоммичены и добавлены в `.gitignore`.
- [ ] Версии зависимостей вынесены в `libs.versions.toml`, а не прописаны
      инлайн в `build.gradle.kts`.

## Выбор структур данных и API

- [ ] Для стека используется `ArrayDeque`, а не устаревший `java.util.Stack`
      (он синхронизирован и медленнее).
- [ ] Для проверки принадлежности символа набору используется `Set<Char>`
      (O(1)), а не `String` + `in` (линейный `indexOf`).
- [ ] Симметричные операции названы симметрично (`push`/`pop`, а не
      `push`/`removeLast()`), и не завязаны на API, доступное только в
      последних версиях JDK/toolchain без необходимости.
- [ ] Если заранее известен размер коллекции — он передаётся в конструктор
      (`ArrayList(size)`), а не оставляется на дефолтный рост.
- [ ] Использованы стандартные удобные функции стдлиба, если они сокращают
      код без потери читаемости (`count { }`, `orEmpty()` вместо ручной
      проверки на `null`).

## Сигнатуры и типы

- [ ] Обобщённая функция вида "трансформация" (`map` и подобные) допускает
      смену типа результата (`T -> R`), а не ограничена одним и тем же типом
      (`T -> T`), если это не обосновано.
- [ ] В Java-обобщениях рассмотрены wildcards (`? extends T`, `? super R`)
      там, где они расширяют применимость метода — и есть понимание, зачем
      именно они нужны в конкретном случае.
- [ ] Проверено поведение при передаче `null` в Java-методы: если аргумент
      не должен быть `null`, это явно задокументировано/провалидировано
      (например, аннотацией `@NullMarked`/`@NonNull`), а не падает
      неожиданным `NullPointerException` без объяснения.

## Именование

- [ ] Нет неловких сочетаний в именах (двойное `is`, лишние приставки).
      Мелкая логика вроде проверки одного символа лучше выносится в
      отдельную extension-функцию с понятным именем (`Char.isVowel()`).

## Видимость

- [ ] Внутренние счётчики/состояние, нужные только для тестов, имеют
      минимально необходимую видимость (`internal` в Kotlin,
      package-private в Java), а не `public`.

## Работа с SharedPreferences / делегатами

- [ ] `commit()`/`apply()` не "прошиваются" внутрь делегата — вызывающий
      код сам решает, когда сохранять изменения.
- [ ] `edit()` не вызывается на каждое изменение поодиночке — понимание,
      что это атомарная операция с созданием нового `Editor`, и запись
      должна батчиться корректно.

## Тесты

- [ ] Однотипные тесты для разных реализаций (Kotlin/Java и т.п.) не
      дублируются копипастой — данные и кейсы выносятся в общий
      ресурс/маппинг (по аналогии с JSON-кейсами + `DynamicTest`).
- [ ] В тестах используется `TestReporter`, а не `println`, чтобы вывод
      попадал в HTML/XML-отчёты, а не терялся в stdout.
- [ ] Для алгоритмических задач (там, где это оправдано затратами) стоит
      рассмотреть стресс-тесты: генератор случайных входных данных +
      проверка результата заведомо простым/эталонным алгоритмом, много
      итераций.

## Мёртвый код

- [ ] Нет неиспользуемых конструкторов, полей, методов — если что-то не
      используется, оно удаляется, а не остаётся "на всякий случай".
